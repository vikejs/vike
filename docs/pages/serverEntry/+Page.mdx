`+serverEntry.js` enables you to control how the server starts. You can define it either:
- With `+server.js` => `+serverEntry.js` wraps your `+server.js` in production.
- Without `+server.js` => `+serverEntry.js` defines the entire server (for both development and production) — it gives you more control than `+server.js`.

See explanation at: <Link href="#with-out-server-js" />.

Use case examples:
- Deploy to a platform without built-in support, <Link href="#example-aws-lambda">e.g. AWS Lambda</Link>
- Use a server framework without built-in support (e.g. [Koa](https://github.com/koajs/koa) or [hapi](https://github.com/hapijs/hapi))
- Use non-Node.js server APIs, such as `Bun.serve()` or `Deno.serve()`
- Use all CPU cores with Node.js's [`cluster`](https://nodejs.org/api/cluster.html) module

> See also:
> - <Link href="/server" />
> - <Link href="/server#extra-control" />

> If you don't define `+serverEntry.js`:
> - In development, Vite's built-in development server acts as the entry.
> - In production, Vike's built-in server entry uses [srvx](https://srvx.h3.dev) (which has first-class support for Node.js, Bun, and Deno).


## With(out) `+server.js`

### With `+server.js`

If you define both `+serverEntry.js` and `+server.js`, then `+serverEntry.js` wraps `+server.js` and is only used for production.

> In development, Vite's development server acts as the entry: your `+server.js` is attached to Vite's development server. Consequently, `+serverEntry.js` isn't used in development. In other words: `+serverEntry.js` never runs in development.

> The typical use case is to customize a deployment integration, see <Link href="#example-aws-lambda" />.

```ts
// +serverEntry.ts

// Wrapping +server.ts — only in production

// Your +server.js exports
import server from 'vike:server'

// startServer() can be anything, typically a deployment tool
startServer({
  port: 3000,
  onRequest: (request) => server.fetch(request)
})
```

```bash
# Build: +serverEntry.ts => dist/server/index.mjs
$ vike build
# Run +serverEntry.ts
$ node dist/server/index.mjs
```

### Without `+server.js`

If you don't define `+server.js`, then `+serverEntry.js` defines the entire server (for both development and production).

```ts
// +serverEntry.ts

// Defines the entire server — both development and production

// You can also use Vike's low-level server integration primitives for full control
import { renderPage } from 'vike/server'

const app = express()

// ...

// Unlike +server.js, note how +serverEntry.js determines how the server starts:
express.listen(3000)
```

See full example at: <Link href="/renderPage#usage" />.

> `+serverEntry.js` is responsible for starting the server, whereas with `+server.js` the server is started by Vite in development and by [srvx](https://srvx.h3.dev) in production.

> In development, when you modify `+serverEntry.js` (or a file it imports), Vike automatically restarts your server process.

> If you want to use HTTPS in development, use HTTPS in your server and also [pass the HTTPS certificates to Vite](https://vite.dev/config/server-options.html#server-https) (Vite uses them for its HMR WebSocket).

```bash
# Build: +serverEntry.ts => dist/server/index.mjs
$ vike build
# Run +serverEntry.ts
$ node dist/server/index.mjs
```


## Example: AWS Lambda

AWS Lambda calls the `handler()` function exported by `dist/server/index.mjs`. You can implement it natively or with srvx.

The examples below use `+serverEntry.js` with <Link href="/server">`+server.js`</Link>, which means that `+serverEntry.js` is only used in production — see <Link href="#with-out-server-js" />.

> With AWS Lambda, you usually serve the static assets `dist/client/` with a CDN, such as Amazon CloudFront.

### Native

```ts
// +serverEntry.ts (with +server.js)

import type { APIGatewayProxyHandlerV2 } from 'aws-lambda'
import server from 'vike:server'

// AWS Lambda calls handler() for each request (Lambda function URL or API Gateway HTTP API)
export const handler: APIGatewayProxyHandlerV2 = async (event) => {
  // AWS Lambda event => Request
  const url = new URL(`https://${event.requestContext.domainName}${event.rawPath}`)
  url.search = event.rawQueryString
  const headers = new Headers(event.headers as Record<string, string>)
  if (event.cookies) headers.set('cookie', event.cookies.join('; '))
  const body = event.body ? Buffer.from(event.body, event.isBase64Encoded ? 'base64' : 'utf8') : undefined
  const request = new Request(url, { method: event.requestContext.http.method, headers, body })

  // Your +server.js exports
  const response = await server.fetch(request)

  // Response => AWS Lambda result
  return {
    statusCode: response.status,
    headers: Object.fromEntries([...response.headers].filter(([name]) => name !== 'set-cookie')),
    cookies: response.headers.getSetCookie(),
    body: Buffer.from(await response.arrayBuffer()).toString('base64'),
    isBase64Encoded: true
  }
}
```

### srvx

```ts
// +serverEntry.ts (with +server.js)

import { toLambdaHandler } from 'srvx/aws-lambda'
import server from 'vike:server'

// AWS Lambda calls handler() for each request
export const handler = toLambdaHandler({ fetch: server.fetch })
```


## Example: Bun

Without `+serverEntry.js`, `$ bun dist/server/index.mjs` runs Vike's built-in server entry powered by [srvx](https://srvx.h3.dev) which automatically uses `Bun.serve()` under the hood. But only in production: in development, `$ vike dev` uses Vite's development server ([which uses the Node.js server APIs](https://github.com/vitejs/ecosystem/issues/16) instead of `Bun.serve()`).

With `+serverEntry.js` (and without `+server.js`, see <Link href="#with-out-server-js" />), you can use [`Bun.serve()`](https://bun.com/docs/runtime/http/server) in both development and production. For example to use Bun's [WebSockets](https://bun.com/docs/runtime/http/websockets) also in development:

```ts
// +serverEntry.ts (without +server.js)

import assert from 'node:assert'
import { getGlobalContext } from 'vike'
import { renderPage } from 'vike/server'
import { fetchNodeHandler } from 'srvx/node'
import type { IncomingMessage, ServerResponse } from 'node:http'

const globalContext = await getGlobalContext()
assert(!globalContext.isClientSide)

Bun.serve({
  port: 3000,
  async fetch(request) {
    if (import.meta.env.DEV) {
      const { devMiddleware } = globalContext
      assert(devMiddleware) // TypeScript narrowing
      // Vite's development middleware, through srvx's emulation of Node.js's req/res
      let handled = true
      const response = await fetchNodeHandler(
        (req: IncomingMessage, res: ServerResponse, next?: () => void) =>
          devMiddleware(req, res, () => {
            handled = false
            next?.()
          }),
        request
      )
      if (handled) return response
    } else {
      // Serve the static assets (dist/client/)
      const file = Bun.file(`${import.meta.dirname}/../client${new URL(request.url).pathname}`)
      if (await file.exists()) return new Response(file)
    }
    const { httpResponse } = await renderPage({ urlOriginal: request.url, headersOriginal: request.headers })
    return new Response(httpResponse.getReadableWebStream(), {
      status: httpResponse.statusCode,
      headers: httpResponse.headers
    })
  }
})
```

```bash
# Development (with package.json#scripts.dev set to "vike dev")
$ bun --bun run dev
# Production
$ vike build
$ bun dist/server/index.mjs
```

> `Deno.serve()` should work the same way.

> Vite's development middleware is a [Connect](https://github.com/senchalabs/connect) middleware (it uses Node.js's `req`/`res`), which is why it needs a bridge such as srvx's `fetchNodeHandler()`. Vite wants to move away from Connect, see [vitejs/ecosystem#16](https://github.com/vitejs/ecosystem/issues/16).


## `vike:server`

`import server from 'vike:server'` is your <Link href="/server">`+server.js`</Link> exports (e.g. `{ fetch }`).

> If you don't define `+server.js`, then it's the exports of Vike's built-in server.

It's typically used for wrapping `+server.js`, for example:

```ts
// +serverEntry.ts

import { serve } from 'srvx'
import server from 'vike:server'

serve({
  port: 3000,
  fetch(request) {
    if (new URL(request.url).pathname === '/health') return new Response('OK')
    return server.fetch(request)
  }
})
```


## Static assets

When using `+serverEntry.js`, it's your responsibility to serve the static assets `dist/client/`.

> If you don't use `+serverEntry.js`, then Vike's built-in server automatically serves the static assets.

> See <Link href="/precompress" noBreadcrumb /> to generate `.br`/`.gz` files for your static assets at build time.


## Pre-rendering

<Link href="/pre-rendering">Pre-rendering</Link> doesn't execute `+serverEntry.js`.

> If all your pages are pre-rendered, `dist/server/` is still kept (Vike otherwise removes it, see <Link href="/prerender#keepdistserver" doNotInferSectionTitle />).
