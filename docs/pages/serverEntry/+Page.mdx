Define `+serverEntry.js` to control how your server starts: Vike builds it into `dist/server/index.mjs`, the file you run in production.

> Without `+server.js`, `$ vike dev` also runs `+serverEntry.js` in development, see <Link href="#development" />.

```ts
// +serverEntry.ts

// Your +server.js exports, e.g. `{ fetch }`
import server from 'vike:server'

// startServer() can be anything, typically a deployment or server tool
startServer({
  port: 3000,
  onRequest: (request) => server.fetch(request)
})
```

```bash
# Build: +serverEntry.ts => dist/server/index.mjs
$ vike build
# Run +serverEntry.ts
$ node dist/server/index.mjs
```

It gives you full control over your server entry, for example to:
- Deploy to a platform without built-in support, e.g. AWS Lambda (see example below)
- Use another server framework or runtime API such as `Bun.serve()` and `Deno.serve()`
- Use all CPU cores with Node.js's [`cluster`](https://nodejs.org/api/cluster.html) module

> For even more control, you can manually integrate Vike into your server with <Link href="/renderPage">`renderPage()`</Link>, see <Link href="#development" />.

> Without `+serverEntry.js`, `dist/server/index.mjs` is Vike's built-in server entry: a [srvx](https://srvx.h3.dev) server entry with first-class support for Node.js, Deno, and Bun (and potentially future runtimes). See also: <Link href="/server" />.

> Vike uses <Link href="/blog/universal-deploy">Universal Deploy</Link> under the hood: it provides Vike's built-in server and integrates with deployment providers (e.g. Cloudflare and Vercel).


## `vike:server`

`import server from 'vike:server'` is your <Link href="/server">`+server.js`</Link> exports, e.g. `{ fetch }`. (If you don't define `+server.js`, then it's Vike's built-in server.)

You can use it to handle requests before they reach `+server.js`:

```ts
// +serverEntry.ts

import { serve } from 'srvx'
import server from 'vike:server'

serve({
  port: 3000,
  fetch(request) {
    if (new URL(request.url).pathname === '/health') return new Response('OK')
    return server.fetch(request)
  }
})
```


## Example: AWS Lambda

AWS Lambda calls the `handler()` function exported by `dist/server/index.mjs`. You can implement it natively or with srvx.

> With AWS Lambda, you usually serve the static assets `dist/client/` with a CDN, such as Amazon CloudFront.

The examples below use `+serverEntry.js` with <Link href="/server">`+server.js`</Link>, which means that `+serverEntry.js` is only used in production: in development, `$ vike dev` runs your `+server.js` with Vite's development server as usual (see <Link href="#development" />).

### Native

```ts
// +serverEntry.ts (with +server.js)

import type { APIGatewayProxyHandlerV2 } from 'aws-lambda'
import server from 'vike:server'

// AWS Lambda calls handler() for each request (Lambda function URL or API Gateway HTTP API)
export const handler: APIGatewayProxyHandlerV2 = async (event) => {
  // AWS Lambda event => Request
  const url = new URL(`https://${event.requestContext.domainName}${event.rawPath}`)
  url.search = event.rawQueryString
  const headers = new Headers(event.headers as Record<string, string>)
  if (event.cookies) headers.set('cookie', event.cookies.join('; '))
  const body = event.body ? Buffer.from(event.body, event.isBase64Encoded ? 'base64' : 'utf8') : undefined
  const request = new Request(url, { method: event.requestContext.http.method, headers, body })

  // Your +server.js exports
  const response = await server.fetch(request)

  // Response => AWS Lambda result
  return {
    statusCode: response.status,
    headers: Object.fromEntries([...response.headers].filter(([name]) => name !== 'set-cookie')),
    cookies: response.headers.getSetCookie(),
    body: Buffer.from(await response.arrayBuffer()).toString('base64'),
    isBase64Encoded: true
  }
}
```

### srvx

```ts
// +serverEntry.ts (with +server.js)

import { toLambdaHandler } from 'srvx/aws-lambda'
import server from 'vike:server'

// AWS Lambda calls handler() for each request
export const handler = toLambdaHandler({ fetch: server.fetch })
```


## Development

#### With `+server.js` => production only

If you define <Link href="/server">`+server.js`</Link>, then `+serverEntry.js` is only run in production: in development, Vite's development server is used while `+server.js` is attached to Vite's development server — in other words, Vite's development server *is* the "server entry".

#### Without `+server.js` => also development

If you don't define `+server.js`, then `+serverEntry.js` is also run in development. See an example of using `+serverEntry.js` for both development and production at: <Link href="/renderPage#usage" />.

Note that:
- `+serverEntry.js` is processed by Vite: TypeScript, path aliases, Vite plugins, and `import.meta.env.DEV` work (no need for `tsx`/`ts-node`).
- When you modify `+serverEntry.js` (or a file it imports), your server is automatically restarted. Modifying a page doesn't restart your server: the page is updated with <Link href="/glossary#hmr">HMR</Link> as usual.

> If you want to use HTTPS in development, use HTTPS in your server and also [pass the HTTPS certificates to Vite](https://vite.dev/config/server-options.html#server-https) (Vite uses them for its HMR WebSocket).


## Example: Bun

Without `+serverEntry.js`, `$ bun dist/server/index.mjs` runs Vike's built-in server entry powered by srvx which automatically uses `Bun.serve()` under the hood. But only in production: in development, `$ vike dev` uses Vite's development server (and thus the Node.js server APIs instead of `Bun.serve()`).

With `+serverEntry.js` (and without `+server.js`, see <Link href="#development" />), you can use [`Bun.serve()`](https://bun.com/docs/runtime/http/server) in both development and production, for example to use Bun's [WebSockets](https://bun.com/docs/runtime/http/websockets) also in development:

```ts
// +serverEntry.ts (without +server.js)

import { createDevMiddleware, renderPage } from 'vike/server'
import { fetchNodeHandler } from 'srvx/node'

const devMiddleware = import.meta.env.DEV ? (await createDevMiddleware()).devMiddleware : null

Bun.serve({
  port: 3000,
  async fetch(request) {
    if (devMiddleware) {
      // Vite's development middleware, through srvx's emulation of Node.js's req/res
      let handled = true
      const response = await fetchNodeHandler(
        (req, res, next) =>
          devMiddleware(req, res, () => {
            handled = false
            next()
          }),
        request
      )
      if (handled) return response
    } else {
      // Serve the static assets (dist/client/)
      const file = Bun.file(`${import.meta.dirname}/../client${new URL(request.url).pathname}`)
      if (await file.exists()) return new Response(file)
    }
    const { httpResponse } = await renderPage({ urlOriginal: request.url, headersOriginal: request.headers })
    return new Response(httpResponse.getReadableWebStream(), {
      status: httpResponse.statusCode,
      headers: httpResponse.headers
    })
  }
})
```

```bash
# Development (with package.json#scripts.dev set to "vike dev")
$ bun --bun run dev
# Production
$ vike build
$ bun dist/server/index.mjs
```

> `Deno.serve()` should work the same way.

> Vite's development middleware is a [Connect](https://github.com/senchalabs/connect) middleware (it uses Node.js's `req`/`res`), which is why it needs a bridge such as srvx's `fetchNodeHandler()`. Vite wants to move away from Connect, see [vitejs/ecosystem#16](https://github.com/vitejs/ecosystem/issues/16).


## Static assets

When using `+serverEntry.js`, it's your responsibility to serve the static assets `dist/client/`.

> If you don't use `+serverEntry.js`, then Vike's built-in server automatically serves the static assets.

> See <Link href="/precompress" noBreadcrumb /> to generate `.br`/`.gz` files for your static assets at build time.


## Pre-rendering

<Link href="/pre-rendering">Pre-rendering</Link> doesn't execute `+serverEntry.js`.

> If all your pages are pre-rendered, `dist/server/` is still kept (Vike otherwise removes it, see <Link href="/prerender#keepdistserver" doNotInferSectionTitle />).
